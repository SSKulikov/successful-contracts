Вот основное ТЗ
1. Цель проекта
Разработать MVP веб-приложения для согласования документов (договоры, УПД, счета на оплату, акты, товарные накладные, в перспективе – сметы). Приложение должно обеспечивать:
создание компаний и управление сотрудниками (только админом);
маршрутизацию документов по ролям или конкретным сотрудникам;
две основные сущности для пользователя: «мои документы» и «мои согласования»;
распознавание ключевых полей из загруженных файлов с помощью ИИ (опционально на первом этапе);
минималистичный интерфейс, простую логику, возможность расширения.

2. Роли и регистрация
2.1. Только админ регистрирует компанию
Регистрация доступна только пользователям с правами админа (первый пользователь создаёт компанию).
При регистрации админ указывает: название компании, свои ФИО, email, пароль.

2.2. Админ создаёт сотрудников
У админа есть раздел «Админ панель» → «Создание сотрудников».
Для каждого сотрудника админ задаёт: имя, email, должность, роль, одноразовый пароль.
Админ может: редактировать, сбросить пароль, помечать сотрудника как удалённого (см. п.4.2.1).
Сотрудники не могут зарегистрироваться сами.

3. Вход и первый вход сотрудника
Стандартная страница входа (логин/пароль).
При первом входе с одноразовым паролем – обязательная смена пароля.

4. Личный кабинет
4.1. Вкладки для обычного сотрудника
Мои документы
– все документы, где сотрудник является инициатором (создателем) или автором последней доработки.
– Фильтры: по статусу, типу документа, дате. Поиск по номеру, контрагенту, ИНН.
– Выгрузка в Excel (только из этой вкладки). В выгружаемом файле для каждой строки должна быть ссылка на документ на сайте (прямой URL).
– Для документов со статусом «на доработке»: возможность редактировать и повторно отправить.

Мои согласования
– документы, которые направлены конкретно этому сотруднику (по правилам маршрута).
– Действия: «Согласовать», «Отклонить», «Отправить на доработку» (с обязательным комментарием).

Профиль
– аватар, смена имени, смена пароля (с подтверждением текущего). Никаких списков документов.

4.2. Дополнительные вкладки для админа
Админ панель

Управление сотрудниками:
– список сотрудников, возможность редактировать, сбросить пароль, удалить (soft delete).
– При удалении сотрудник помечается как «удалённый», его имя в истории заменяется на «Удалённый пользователь» (серым цветом). Все документы, созданные им или направленные ему, сохраняются и остаются доступными для просмотра.

Управление маршрутами согласования:
– Админ создаёт маршруты для каждого типа документа отдельно.
– Каждый этап маршрута может быть задан одним из двух способов:

Конкретный сотрудник – задача направляется только этому сотруднику.

Роль + сотрудник по умолчанию – администратор выбирает роль (например, «юрист») и конкретного сотрудника из числа тех, у кого эта роль. Задача направляется этому сотруднику. (Остальные сотрудники с той же ролью не видят задачу, если только администратор не переназначит её позже вручную – на MVP переназначение не требуется).
– Пример: этап 1: роль «юрист», сотрудник «Иванов И.», этап 2: конкретный сотрудник «Петрова А.».

5. Работа с документами
5.1. Загрузка документа
Кнопка «Загрузить документ» на странице «Мои документы».

Выбор файла (PDF, DOCX, JPG/PNG).
Модальное окно с единым набором полей для всех типов документов (на MVP):
тип документа (выпадающий список: договор, УПД, счёт, акт, накладная),
номер документа,
дата,
наименование заказчика, ИНН заказчика,
наименование исполнителя, ИНН исполнителя,
сумма,
основание/предмет договора,
дополнительное поле «Примечание» (текст, необязательно).
Кнопка «Отправить на согласование» (сразу, без промежуточных статусов).

5.2. Статусы документов
на согласовании – документ ожидает решения текущего назначенного сотрудника.

на доработке – возвращён инициатору с замечаниями.
отклонён – окончательно отклонён на любом этапе.
согласован – успешно пройдены все этапы (архивируется).

5.3. Процесс согласования
Сотрудник видит документы, направленные лично ему (во вкладке «Мои согласования»).

Согласовать – документ переходит на следующий этап маршрута. Если этап был последним – статус «согласован».

Отклонить – статус «отклонён».

Отправить на доработку – требуется комментарий; статус становится «на доработке», документ возвращается инициатору.

После доработки и повторной отправки документ начинает проходить маршрут с самого первого этапа (согласно требованию заказчика «с начала по кругу»).

5.4. Уведомления
Внутри веб-интерфейса: лента уведомлений (или иконка с бейджем) о новых согласованиях, возвратах на доработку, завершениях.

На MVP – только внутренние уведомления.

6. Особенности для админа
В разделе «Мои документы» админ видит все документы компании (всех сотрудников).

Админ также может загружать документы от своего имени и проходить согласование, если его роль/имя указаны в маршруте.

Админ управляет маршрутами и сотрудниками через админ-панель.

7. Требования к ИИ-распознаванию (отложено)
В будущем при загрузке файла ИИ автоматически заполняет поля: номер, дата, заказчик (наименование и ИНН), исполнитель (наименование и ИНН), сумма, основание.

Не распознавать: БИК, расчётные счета и т.п.

На MVP – считывание ключевых файлов через ИИ и автозаполнение форм с возможностью исправления вручную

8. Общие требования
Минимум вкладок: 3 для сотрудника, 4 для админа.

Выгрузка в Excel – только из «Мои документы», с обязательной ссылкой на документ.

Технологии – на усмотрение разработчика.

9. Приоритет разработки (по желанию заказчика)
Логика согласования (ядро).

Ручной ввод документов, маршруты, вкладки.
Админ-панель (сотрудники, маршруты).
Уведомления и выгрузка Excel.
ИИ-распознавание – позже.

Возможность добавить смету, интеграции с 1С и учётом – в следующих версиях.

10. Docker Hub build/push и деплой

Ниже описан ручной production-путь без сборки исходников на VPS: локально собираются Docker-образы, пушатся в Docker Hub, а Portainer скачивает готовые `api` и `web` images.

10.1. Предварительные требования

Установлены:

```bash
docker --version
docker buildx version
node --version
npm --version
```

Перед push нужно войти в Docker Hub:

```bash
docker login
```

Во всех командах ниже замените `DOCKERHUB_USERNAME` на имя Docker Hub аккаунта.

10.2. Backend image

Backend собирается из `server/pdf-parser/Dockerfile`.

```bash
docker buildx build \
  --platform linux/amd64 \
  -t DOCKERHUB_USERNAME/successful-contracts-api:latest \
  -f server/pdf-parser/Dockerfile \
  ./server/pdf-parser \
  --push
```

Если сборка на Mac нестабильна из-за Docker Desktop/network, повторите команду или очистите build cache:

```bash
docker builder prune -af
```

10.3. Frontend image

Frontend лучше собирать в два шага: сначала Vite `dist`, потом nginx-образ с готовой статикой. Это исключает `npm ci` из Docker build фронта.

```bash
cd client/pdf-parser-ui
VITE_API_URL=/api \
VITE_USE_MOCK_API=false \
VITE_USE_MOCK_ADMIN_API=false \
VITE_USE_MOCK_PROFILE_API=false \
npm run build
cd ../..
```

После этого собрать и запушить nginx image:

```bash
docker buildx build \
  --platform linux/amd64 \
  -t DOCKERHUB_USERNAME/successful-contracts-web:latest \
  -f client/pdf-parser-ui/Dockerfile.prebuilt \
  ./client/pdf-parser-ui \
  --push
```

Важно: для production со встроенным nginx proxy используйте `VITE_API_URL=/api`. Тогда браузер будет обращаться к API через тот же origin: `/api/auth/login`, `/api/documents/...` и т.д.

10.4. Docker Compose для Portainer

В Portainer можно создать stack через Web editor и указать готовые Docker Hub images:

```yaml
services:
  redis:
    image: redis:7-alpine
    restart: unless-stopped
    volumes:
      - redis_data:/data
    command: ["redis-server", "--appendonly", "yes"]

  api:
    image: DOCKERHUB_USERNAME/successful-contracts-api:latest
    restart: unless-stopped
    environment:
      NODE_ENV: production
      TRUST_PROXY: ${TRUST_PROXY:-1}
      DATABASE_URL: ${DATABASE_URL}
      JWT_SECRET: ${JWT_SECRET}
      JWT_EXPIRES_IN: ${JWT_EXPIRES_IN:-7d}
      PUBLIC_APP_URL: ${PUBLIC_APP_URL}
      CORS_ORIGIN: ${CORS_ORIGIN}
      REDIS_URL: redis://redis:6379

      STORAGE_PROVIDER: ${STORAGE_PROVIDER:-s3}
      S3_ENDPOINT: ${S3_ENDPOINT}
      S3_REGION: ${S3_REGION}
      S3_BUCKET_RAW: ${S3_BUCKET_RAW}
      S3_BUCKET_PROCESSED: ${S3_BUCKET_PROCESSED}
      S3_ACCESS_KEY_ID: ${S3_ACCESS_KEY_ID}
      S3_SECRET_ACCESS_KEY: ${S3_SECRET_ACCESS_KEY}
      S3_FORCE_PATH_STYLE: ${S3_FORCE_PATH_STYLE:-false}
      S3_PRESIGNED_UPLOAD_TTL_SEC: ${S3_PRESIGNED_UPLOAD_TTL_SEC:-900}
      S3_PRESIGNED_DOWNLOAD_TTL_SEC: ${S3_PRESIGNED_DOWNLOAD_TTL_SEC:-900}

      PARSER_MAX_FILE_MB: ${PARSER_MAX_FILE_MB:-30}
      PARSER_JOB_TIMEOUT_MS: ${PARSER_JOB_TIMEOUT_MS:-120000}
      LLM_PROVIDER: ${LLM_PROVIDER:-gigachat}
      NODE_TLS_REJECT_UNAUTHORIZED: ${NODE_TLS_REJECT_UNAUTHORIZED:-0}
      GIGA_CHAT_ACCESS_KEY: ${GIGA_CHAT_ACCESS_KEY}
      OAUTH_TOKEN: ${OAUTH_TOKEN:-}
      FOLDER_ID: ${FOLDER_ID:-}
      BEARER_TOKEN: ${BEARER_TOKEN:-}
    volumes:
      - api_uploads:/app/uploads
      - api_storage_tmp:/app/storage
    depends_on:
      - redis

  web:
    image: DOCKERHUB_USERNAME/successful-contracts-web:latest
    restart: unless-stopped
    depends_on:
      - api
    ports:
      - "${WEB_PORT:-8080}:80"

volumes:
  redis_data:
  api_uploads:
  api_storage_tmp:
```

Минимальные переменные окружения для Portainer stack:

```env
WEB_PORT=8080
PUBLIC_APP_URL=http://your-domain.example:8080
CORS_ORIGIN=http://your-domain.example:8080
TRUST_PROXY=1

DATABASE_URL=mysql://USER:PASSWORD@HOST:3306/DATABASE
JWT_SECRET=replace-with-long-random-secret
JWT_EXPIRES_IN=7d

STORAGE_PROVIDER=s3
S3_ENDPOINT=https://storage.yandexcloud.net
S3_REGION=ru-central1
S3_BUCKET_RAW=contracts-raw-prod
S3_BUCKET_PROCESSED=contracts-processed-prod
S3_ACCESS_KEY_ID=replace-me
S3_SECRET_ACCESS_KEY=replace-me
S3_FORCE_PATH_STYLE=false

LLM_PROVIDER=gigachat
NODE_TLS_REJECT_UNAUTHORIZED=0
GIGA_CHAT_ACCESS_KEY=replace-me
```

10.5. Проверка после деплоя

Проверить health:

```bash
curl http://your-domain.example:8080/health
```

Ожидаемый ответ:

```json
{"status":"ok","service":"pdf-parser"}
```

Если браузер пытается ходить на `localhost:3003`, frontend image собран неправильно. Пересоберите `dist` с `VITE_API_URL=/api`, затем заново соберите и запушьте `successful-contracts-web:latest`.
