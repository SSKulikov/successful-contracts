# Техническое задание  
## Система обработки и согласования документов

## 1. Назначение проекта
Разработать веб-приложение для компаний малого и среднего бизнеса, которое позволяет:
- загружать документы (договоры, УПД, счета и др.);
- автоматически извлекать ключевые поля из файла;
- хранить документы и версии файлов в едином пространстве;
- запускать маршруты согласования;
- отслеживать статусы, ответственных и историю изменений.

Ключевая бизнес-цель: повысить прозрачность документооборота и сократить время согласования.

## 2. Границы проекта

### 2.1. Входит в проект
- Frontend-приложение (React + TypeScript + Vite).
- Backend API для парсинга и сохранения данных.
- База данных для хранения пользователей, документов, маршрутов и истории.
- Ролевая модель доступа (админ/сотрудник + функциональные роли).

### 2.2. Не входит в текущий этап
- Полноценный внешний бренд-дизайн (финальные фирменные цвета, айдентика).
- Интеграции с внешними DMS/ERP.
- Мобильное приложение.

## 3. Целевые роли пользователей

### 3.1. Сотрудник
- Загружает документы.
- Просматривает доступные документы.
- Участвует в согласовании на назначенных этапах.
- Редактирует профиль.

### 3.2. Администратор
- Полный доступ в рамках своей компании.
- Управляет сотрудниками и ролями.
- Настраивает маршруты согласования.
- Может переназначать текущего согласующего.

## 4. Бизнес-правила

### 4.1. Мультиарендность
- Каждый пользователь относится к одной компании.
- Пользователи компании не видят данные других компаний.

### 4.2. Жизненный цикл документа
Статусы:
- `draft` (черновик);
- `in_approval` (на согласовании);
- `approved` (согласован);
- `rejected` (отклонен);
- `returned` (возвращен на доработку);
- `archived` (архив, по решению администратора).

### 4.3. Редактирование документа
- В статусе `draft` редактирование разрешено.
- После отправки на согласование редактирование запрещено.
- После возврата на доработку редактирование снова разрешено.

### 4.4. Удаление
- Физическое удаление документа не выполняется.
- Используется архивирование.

### 4.5. Статус сотрудника
- `active` / `inactive`.
- Неактивный пользователь не может входить в систему.
- Активные задачи согласования должны быть переназначены.

## 5. Функциональные требования

### 5.1. Авторизация и учетные записи
- Единая форма входа/регистрации (UX).
- Хранение пароля только в хэшированном виде.
- Разграничение доступа по ролям.

### 5.2. Работа с документами
- Загрузка файла (`pdf`, `doc`, `docx`, при необходимости изображения).
- Автозаполнение полей документа после парсинга.
- Ручная корректировка автозаполненных данных.
- Сохранение данных документа.
- Хранение версий файла.

### 5.3. Согласование
- Для типа документа назначается маршрут согласования.
- Маршрут состоит из этапов с последовательным прохождением.
- Этап может быть назначен:
  - на конкретного сотрудника;
  - на функциональную роль (используется основной ответственный).
- Если у роли нет основного ответственного, маршрут невалиден.

### 5.4. Действия согласующего
- Согласовать -> переход к следующему этапу.
- Отклонить -> завершение процесса (`rejected`).
- Вернуть на доработку -> инициатору (`returned`).

### 5.5. Повторный запуск после доработки
- После повторной отправки документ запускается с первого этапа маршрута.

### 5.6. История действий
Фиксируются:
- создание документа;
- отправка на согласование;
- согласование/отклонение/возврат;
- изменение данных документа;
- загрузка новой версии файла;
- переназначение согласующего.

### 5.7. Права доступа
- Сотрудник:
  - видит доступные ему документы;
  - согласует этапы, назначенные на него;
  - редактирует профиль.
- Админ:
  - полный доступ в рамках компании;
  - управление пользователями;
  - управление маршрутами;
  - ручное переназначение согласования.

## 6. Интерфейс и пользовательские страницы

### 6.1. Главная страница
- Заголовок и краткое описание продукта.
- Название компании текущего пользователя.
- Показатели:

- Основные CTA-кнопки:

  - вход в систему.
- Блок преимуществ (минимум 3 карточки).
- Блок "Последние действия" (последние события по документам).

### 6.2. Авторизация
- Единая страница с переключением вкладок:
  - вход;
  - регистрация.

### 6.3. Раздел "Договоры"
- Форма документа.
- Кнопка загрузки файла для автозаполнения.
- Редактируемые поля документа.
- Отправка данных на сохранение.

### 6.4. Все документы (следующий этап)
- Таблица с колонками:
  - тип;
  - название;
  - контрагент;
  - номер;
  - дата;
  - сумма;
  - статус;
  - инициатор;
  - текущий этап.
- Поиск и фильтры.
- Экспорт в Excel.
- Переход в карточку документа.

### 6.5. Документы на согласовании (следующий этап)
- Вкладка "Загруженные мной".
  - отображаются: статус, текущий этап.
- Вкладка "Требуют моего решения".
  - доступны действия: согласовать, отклонить, вернуть на доработку.

### 6.6. Карточка документа (следующий этап)
- Основные данные (все поля документа).
- Файл:
  - скачать;
  - предпросмотр (если поддерживается формат).
- Версии файла (список версий).
- Маршрут:
  - этапы;
  - статусы;
  - комментарии.
- История действий.
- Доступные действия по роли:
  - согласовать;
  - отклонить;
  - вернуть на доработку;
  - комментарий.

### 6.7. Профиль (следующий этап)
- Данные пользователя:
  - имя;
  - должность;
  - аватар;
- смена пароля;
- форма обратной связи.

### 6.8. Админ-раздел (следующий этап)
- Сотрудники:
  - создание;
  - редактирование;
  - деактивация;
  - сброс пароля (временный пароль);
  - назначение ролей.
- Роли:
  - создание;
  - назначение сотрудников;
  - назначение основного ответственного.
- Маршруты согласования:
  - настройка этапов;
  - порядок этапов;
  - назначение: сотрудник / роль.

### 6.9. Создание документа (следующий этап)
- Форма:
  - тип;
  - файл;
  - контрагент;
  - номер;
  - дата;
  - сумма;
  - комментарий.
- AI:
  - автозаполнение полей;
  - возможность ручной корректировки пользователем.
- Кнопки:
  - сохранить как черновик;
  - отправить на согласование.

## 7. Модель данных (ключевые сущности)

### 7.1. Company
- `id`
- `name`
- `inn`
- `settings_json`
- `created_at`
- `updated_at`
- связи:
  - сотрудники;
  - документы;
  - функциональные роли;
  - маршруты согласования.

### 7.2. User
- `id`
- `company_id`
- `first_name`
- `last_name`
- `position`
- `email` (unique within tenant)
- `password_hash`
- `system_role` (`admin` | `employee`)
- `status` (`active` | `inactive`)
- `last_login_at`
- `created_at`
- `updated_at`
- функциональные роли: many-to-many через таблицу связей `user_functional_roles`.

### 7.3. FunctionalRole
- `id`
- `company_id`
- `name` (например: юрист, бухгалтер, финансист)
- `primary_user_id` (обязателен для роли, используемой в маршрутах)

### 7.4. Document
- `id`
- `company_id`
- `type`
- `title`
- `number`
- `date`
- `counterparty`
- `amount`
- `currency`
- `status`
- `initiator_user_id`
- `current_step`
- `current_approver_user_id`
- `created_at`
- `updated_at`

### 7.5. DocumentFileVersion
- `id`
- `document_id`
- `file_path` / `storage_key`
- `file_name`
- `uploaded_by_user_id`
- `uploaded_at`
- `version_number`

### 7.6. ApprovalRoute
- `id`
- `company_id`
- `document_type`
- `name`
- `is_active`

### 7.7. ApprovalRouteStep
- `id`
- `route_id`
- `step_order`
- `assignee_type` (`user` | `functional_role`)
- `assignee_user_id` (nullable)
- `assignee_role_id` (nullable)

### 7.8. ActivityLog
- `id`
- `company_id`
- `document_id` (nullable)
- `actor_user_id`
- `action`
- `payload_json`
- `created_at`

## 8. API-контракты (текущий этап)

### 8.1. Парсинг файла
`POST /api/parse-file`  
Content-Type: `multipart/form-data`, поле `file`.

Успешный ответ (пример):
```json
{
  "message": "File parsed",
  "filename": "contract.docx",
  "path": "/uploads/contract.docx",
  "parsedJson": {
    "supplier": {},
    "customer": {},
    "contract_number": "..."
  }
}
```

### 8.2. Сохранение данных
`POST /api/save-data-info`  
Content-Type: `application/json`.

Тело запроса: плоский JSON с полями формы договора.

## 9. Нефункциональные требования
- Производительность: интерфейс должен оставаться отзывчивым при длительном парсинге файла.
- Безопасность:
  - хэширование паролей;
  - проверка прав доступа на каждом защищенном API;
  - ограничение доступа по компании (tenant isolation).
- Надежность: корректная обработка ошибок API и повторных попыток.
- UX: понятные состояния загрузки, успеха и ошибок.
- Масштабируемость: возможность расширения на новые типы документов и маршрутов.

## 10. Уведомления (минимальный набор)
Внутри системы должны отображаться уведомления о событиях:
- документ на согласовании;
- документ согласован;
- документ отклонен;
- документ возвращен на доработку.

## 13. Критерии приемки
- Пользователь может открыть главную страницу, перейти к авторизации и в раздел договоров.
- В разделе договоров:
  - кнопка выбора файла запускает системный выбор;
  - файл отправляется на парсинг;
  - поля формы автозаполняются;
  - данные формы отправляются на сохранение.
- Для разделов следующих этапов требования считаются выполненными при наличии функционала, перечисленного в разделах `6.4-6.9`.
- Интерфейс адаптируется под мобильную ширину без критических поломок.
- Ошибки API отображаются пользователю понятным сообщением.
- Код успешно проходит сборку.
