# Беклог Dev1 — итерационный план (ядро согласований + UI)

Документ синхронизирован с целями ТЗ и `ROADMAP-DELTA.md` для зоны Dev1: документы, согласования, карточка, экспорт, Redis read-through и интеграция с AI-парсером.

---

## Tech decisions (фикс до старта)

| Область | Решение |
|---------|---------|
| **БД-подход** | Raw SQL в стиле проекта (`employees` / `auth_sessions`) + `ensure*Table` + инкрементальные `ALTER`. |
| **ORM-план** | Prisma-модели для approval-домена - отдельным этапом после стабилизации ядра. |
| **Канон статусов** | В БД/API `snake_case`: `in_approval`, `revision`, `rejected`, `approved` (UI показывает русские лейблы через маппинг). На практике добавлен черновик `uploaded` («Загружен») до первого submit. |
| **Форматы v1** | На первой итерации `PDF/DOCX`, `JPG/PNG` - отдельным инкрементом. |
| **Экспорт** | Целевой endpoint `GET /api/documents/export.xlsx`, ссылка через `PUBLIC_APP_URL`. |

## Этап 2 - Backend API документов

### 2.1 Создание и чтение

- [x] `POST /api/documents`: ручное создание, валидация обязательных полей, событие `document_created`.
- [x] `GET /api/documents/my`:  
  выборка "мои документы" (инициатор или последний редактор), фильтры `status/type/date_from/date_to`, поиск `number/counterparty/inn`.
- [x] `GET /api/documents/my/stats`: сводка `COUNT` по `status` при тех же правилах видимости, что у списка (без фильтров таблицы).
- [x] `GET /api/documents/:id`: карточка документа + текущий этап + история.

### 2.2 Редактирование доработки

- [ ] `PATCH /api/documents/:id`: редактирование только в `revision` и только инициатором/последним редактором. *(Сейчас реализовано для `revision` и `uploaded`.)*
- [x] Событие `document_updated`.

### 2.3 Отправка/переотправка

- [x] `POST /api/documents/:id/submit`: первичный запуск в маршрут.
- [x] `POST /api/documents/:id/resubmit`: повторный запуск после доработки с шага 1.
- [x] Очистка старых активных задач и создание нового цикла.
- [x] Событие `document_resubmitted`.
- [x] `POST /api/documents/:id/withdraw` — отзыв с согласования в `uploaded`, событие `document_withdrawn`.
- [x] `DELETE /api/documents/:id` — удаление документа (ограничения по статусу и правам).
- [x] `GET /api/documents/:id` — в ответе флаги `canWithdrawDocuments`, `canDeleteDocuments`, `canSubmitForApproval`, `canResubmitForApproval`; в истории поле `variant` для UI.

**DoD этапа 2:** сценарий `create -> submit -> revise -> update -> resubmit` воспроизводим через API без ручных SQL-фиксов.

## Этап 3 - Backend API согласований

### 3.1 Мои задачи

- [x] `GET /api/approvals/my`: только задачи текущего сотрудника и только активные/ожидающие решения.
- [x] В ответе списка: сумма документа (`amount`), полных календарных дней с назначения задачи (`waitingDays`), флаг `canTakeDecision` для UI.

### 3.2 Действия

- [ ] `POST /api/approvals/:taskId/approve`: завершение шага, переход на следующий, на последнем шаге -> `approved`. *(Сейчас перехода по маршруту нет, документ закрывается сразу.)*
- [x] `POST /api/approvals/:taskId/reject`: статус документа `rejected`.
- [x] `POST /api/approvals/:taskId/revise`: обязательный `comment` (400, если пусто), статус документа `revision`, возврат инициатору.

### 3.3 История и аудит

- [x] На каждое действие пишется запись в `approval_document_events`.
- [x] В истории отображаются `actor + comment + timestamp`.

**DoD этапа 3:** сценарий `approve/reject/revise` меняет статус документа и историю консистентно.

## Этап 4 - Redis read-through кэш

### 4.1 Инфраструктура

- [x] Модуль `cache/redis.ts`: `getJson/setJson/del`.
- [x] Graceful fallback при недоступном Redis.

### 4.2 Точки кэширования

- [x] `GET /api/documents/:id` -> ключ `doc:{companyId}:{id}`.
- [x] `GET /api/documents/my` -> ключ `my-docs:{companyId}:{hash}` (фильтры запроса + роль + id сотрудника), TTL 120 с.

### 4.3 Инвалидация

- [x] Инвалидация ключа документа `doc:*` и префикса списка `my-docs:{companyId}:*` на `create/edit/submit/approve/reject/revise/resubmit`, а также `withdraw` и `delete`.

**DoD этапа 4:** при down Redis API работает через БД; при up Redis нет stale после mutation.
